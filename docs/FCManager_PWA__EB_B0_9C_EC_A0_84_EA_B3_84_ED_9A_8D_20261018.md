# FCManager — 모바일 PWA 발전 계획

- 작성일: 2026-10-18
- 대상 저장소: https://github.com/jikhanjung/fcmanager
- 운영 서비스: https://fcmanager.app
- 목적: 기존 멀티테넌트 축구 클럽 관리 SaaS를 **일반 회원이 일상적으로 사용하는 모바일 중심 PWA**로 발전시킨다.

## 1. 핵심 목표

FCManager를 새로 개발하거나 클럽마다 별도 앱을 배포하지 않는다. **하나의 Django 기반 멀티테넌트 서비스**를 유지하면서, 각 클럽 회원이 URL 또는 QR코드로 접속하고 필요하면 홈 화면에 설치하도록 한다.

### 사용자 경험 목표

1. 회원은 스마트폰에서 1~2번의 조작으로 **다음 경기 일정과 참석 여부**를 확인한다.
2. 운영진은 경기 일정·변경 사항을 입력하고 **해당 클럽 회원에게 알림**을 보낼 수 있다.
3. 앱을 홈 화면에 추가하면 일반 앱처럼 실행할 수 있다(Android/iPhone).
4. 연결이 불안정해도 최근에 받아둔 일정·경기 결과 등 **읽기 전용 정보**를 확인할 수 있다.
5. 기존의 경기·대회·팀·선수·실시간 중계 및 운영 기능을 훼손하지 않는다.
6. 한 클럽에서 실사용을 검증하되, 모든 구조는 여러 클럽으로 확장 가능하게 유지한다.

### 이번 단계의 비목표

- Android/iOS 네이티브 앱 또는 앱스토어 배포
- 오프라인에서 발생한 편집의 복잡한 양방향 동기화
- 클럽별로 분리된 빌드/도메인/앱 설치 파일
- 결제·요금제 시스템, PostgreSQL 강제 전환
- 실시간 중계의 WebSocket/Redis 전환

## 3. 제품 방향: 운영진 중심 도구에서 회원 중심 앱으로

기존 FCManager의 강점은 경기·대회 관리와 기록·중계다. 신규 투자의 초점은 **일반 회원이 매주 반복 사용하는 화면과 흐름**이다.

### 모바일 홈 화면 제안

- **다음 경기 카드:** 날짜·시간·장소·상대·집합 시간
- **참석 응답:** 참석 / 불참 / 미정 (실제 운영 관행을 확인한 뒤 확정)
- **참석 현황:** 인원 및 본인의 응답 상태
- **최근 공지:** 중요/긴급 공지 우선 표시
- **최근 경기:** 결과와 상세 기록으로 진입
- 클럽 이름·엠블럼·색상 반영; 클럽이 여러 개인 회원은 클럽 전환

초기에는 모바일 브라우저에서도 자연스럽게 동작하도록 만들고, 홈 화면 설치는 **선택 사항**으로 둔다.

### 사용 흐름

1. 운영진이 경기를 등록한다.
2. 해당 클럽 회원에게 공지 또는 푸시가 발송된다(권한 허용 사용자만).
3. 회원이 알림을 누르면 해당 경기 상세/참석 화면이 열린다.
4. 회원은 참석 여부를 응답한다.
5. 운영진은 응답 현황을 보고 필요하면 미응답자에게 재알림한다.
6. 경기 후 기존 FCManager의 결과·이벤트·통계 기능을 이용한다.

**참석 투표 기능이 이미 존재하는지는 확인되지 않았으므로** 신규 모델과 화면이 필요한 후보 기능으로 취급한다.

## 4. 필요한 기술 변경

### 4.1 모바일 UX / 화면 구조

- 현재 Bootstrap 템플릿의 모바일 뷰포트·탐색 동선·터치 영역 점검
- 일반 회원용 홈을 운영진 화면과 구분 (기존 페이지 연결은 유지)
- 가장 자주 쓰는 동작(경기 확인·참석 응답·공지 보기)의 탭 수 최소화
- 일정/경기 상세/공지/알림 설정 화면의 모바일 접근성 확보
- 네트워크 지연·오류·빈 데이터·권한 부족 상태를 명확히 표시

### 4.2 참석 응답 및 일반 회원 권한

- `ClubMembership`과 기존 역할 체계를 검토하여 일반 회원의 **읽기·참석 응답 권한** 정의
- 필요할 경우 `MatchAttendance` 등 클럽·회원·경기와 연결되는 모델 신설
- 응답 변경 마감, 게스트/비회원, 출석 집계 등은 실사용 클럽 운영 규칙을 바탕으로 결정
- 반드시 서버 측에서 `club` 스코핑·권한을 검사 (프런트엔드 숨김만으로 제한하지 않음)
- 동일 사용자 다중 클럽 가입 및 클럽 전환 시 데이터 혼선 방지

### 4.3 PWA 기본 설치 지원

- `manifest.webmanifest` 추가: 앱 이름, 짧은 이름, 아이콘(192/512px), `start_url`, `scope`, `display: standalone`, 테마 색상
- HTTPS 유지, manifest 및 아이콘의 경로/캐시 설정 검증
- Service Worker 등록과 최소 앱 셸 캐싱 적용
- Android/iPhone의 홈 화면 추가 흐름을 실제 기기로 점검
- 클럽별 엠블럼/타이틀을 PWA 설치 아이콘까지 개별화할지는 후속 검토: 단일 공통 PWA로 먼저 시작
- **클럽별 진입 URL과 Service Worker scope 설계**: 하나의 공통 앱 사용 시 플랫폼 루트와 클럽별 경로가 충돌하지 않도록 처리

### 4.4 Web Push 알림

**서버 변경**

- 표준 Web Push(VAPID)를 사용하고, 필요시 `pywebpush` 등 검토
- 회원/기기별 구독 endpoint 및 공개키 저장 모델 설계
- 클럽별 발송 범위 및 수신자 권한 검증
- 구독 만료·취소·실패 처리, 중복 발송 억제 및 발송 로그
- 사용자별 알림 유형/수신 설정 및 탈퇴·권한 해제 시 처리
- 이벤트 발생과 실제 발송을 분리(초기에는 단순 작업 실행, 규모가 커지면 큐/워커 검토)

**클라이언트 변경**

- 사용자의 명시적 조작(예: '알림 받기') 이후 권한 요청
- Service Worker에서 `push`/`notificationclick` 처리
- 알림 클릭 시 해당 클럽의 경기/공지 URL로 이동
- 알림 허용 여부 및 기기별 재구독 상태 안내
- iPhone은 iOS 16.4 이상 **홈 화면에 추가한 웹앱**에서 Web Push 지원; 일반 Safari 탭과 구분
- Android도 브라우저 지원·권한·기기 설정에 따라 수신이 달라짐; 푸시를 유일한 공지 수단으로 가정하지 않음

**처음 지원할 알림 이벤트**

1. 새 경기 일정 등록
2. 경기 일정/장소 변경 또는 취소
3. 중요 공지
4. 참석 마감 전 미응답자 재알림(자동화는 후순위)

### 4.5 오프라인 사용

**1차 목표: 읽기 전용 오프라인**

- Service Worker + Cache Storage로 앱 셸(HTML/CSS/JS/아이콘 등) 캐싱
- 일정/최근 결과 같은 구조화 데이터는 필요 시 IndexedDB에 저장
- '마지막 동기화 시각' 및 '오프라인 데이터' 표시
- 캐시되지 않은 화면, 최신 데이터가 필요한 동작의 실패 처리
- 푸시 구독·로그인·라이브 중계·관리 작업은 온라인이 필요하다고 명시

**캐싱 보안 원칙**

- 다른 클럽/사용자에게 데이터를 노출하지 않도록 로그인 사용자·클럽별 캐시 분리 정책 검토
- 로그아웃/회원 탈퇴/클럽 전환 시 민감 캐시 삭제 또는 무효화
- 인증 응답·개인정보·관리 화면은 기본적으로 무분별하게 Cache Storage에 넣지 않음
- 이미지/영상 등 대용량 자료는 저장 용량과 비용을 고려해 제외하거나 제한
- iOS를 포함해 브라우저가 저장 공간을 정리할 수 있음: 로컬 저장소는 영구 원본이 아님

**후속 옵션: 오프라인 입력**

- 실제 요구가 확인되면 참석 응답/경기 기록을 IndexedDB의 전송 대기열에 보관
- 재시도 시 중복 입력 방지(idempotency key), 수정 충돌 정책, 서버 확정 상태 표시
- iPhone에서는 Background Sync를 전제하지 않고 앱 재개 시 동기화
- 서버 DB를 Source of Truth로 유지

### 4.6 운영/배포/관측

- 기존 `deploy`의 preflight → build → deploy → smoke → rollback 계약 유지
- Service Worker 및 정적 자산 버전 변경 시 오래된 JS/HTML 충돌 방지
- 새 배포 후 업데이트 감지·새로고침 UX 마련
- 푸시 구독 수, 권한 거부율, 발송 성공/실패, 알림 클릭, 참석 응답률 등 기초 지표
- 테스트용 별도 클럽 및 테스트 계정으로 tenant isolation과 푸시 발송 범위 확인
- 운영 DB 백업·미디어 백업·롤백 영향 점검

## 5. 단계별 실행 계획

### Phase 0 — 코드 실사 및 실사용 요구 수집

**작업**

- 현재 `main`의 PWA/Service Worker/manifest/Web Push/참석 기능 존재 여부 조사
- 템플릿과 모바일 페이지 점검, 일반 회원 로그인·온보딩 흐름 확인
- 첫 번째 실사용 축구회의 주간 업무 흐름 파악 (일정 공지, 참석 조사, 취소, 회비 등)
- 실제 운영 환경과 저장소 문서의 버전 차이 확인

**완료 기준:** 재사용 가능한 기존 기능, 추가 모델, 화면 목록, 우선순위가 확정됨.

### Phase 1 — 회원용 모바일 UX 및 참석 기능

**작업**

- 모바일 홈에 다음 경기/공지/최근 결과 배치
- 일반 회원이 해당 클럽의 경기에 참석 응답 가능하게 구현(필요 시)
- 운영진이 참석 현황을 볼 수 있게 구현
- 사용자·클럽 권한 및 반응형 화면 테스트

**완료 기준:** 앱 설치 없이 모바일 브라우저에서 주요 주간 업무를 완료할 수 있음.

### Phase 2 — PWA 설치

**작업**

- manifest/아이콘/Service Worker의 최소 기능 구현
- 홈 화면에서 앱 모드로 실행되도록 설정
- 캐싱 대상 정적 자산 및 갱신 정책 점검
- Android Chrome / iPhone Safari 설치 실측

**완료 기준:** 두 플랫폼에서 홈 화면 추가·실행·업데이트가 정상 동작하고 기존 웹 동선도 유지됨.

### Phase 3 — Web Push

**작업**

- 구독 DB 모델 및 클럽별 발송 API/작업 구현
- 알림 권한 온보딩, 설정, 해지 구현
- 경기 등록·변경·취소·중요 공지 알림 연결
- 수신/비수신/알림 클릭/탈퇴·타 클럽 혼선 테스트

**완료 기준:** 앱이 열려 있지 않을 때도 권한을 허용한 Android/iPhone 회원이 해당 클럽의 알림을 받을 수 있으며, 발송 실패도 안전하게 처리됨.

### Phase 4 — 제한적 오프라인 읽기

**작업**

- 일정 및 최근 결과 읽기 캐시 추가
- 오프라인 배너/마지막 동기화 시각/새 데이터 미수신 안내
- 로그아웃·클럽 전환 시 캐시 무효화 검증
- 업데이트 후 구버전 캐시 동작 시험

**완료 기준:** 한 번 열어 동기화한 주요 정보는 비행기 모드에서도 표시되며, 최신 정보로 오인하지 않도록 안내함.

### Phase 5 — 첫 클럽 실사용 및 범위 결정

**작업**

- 1개 클럽에서 실제 경기 2~4회 운영하며 마찰 지점 기록
- 회원의 홈 화면 설치율, 알림 허용률, 참석 응답률 조사
- 반복 요구(회비·선수 선정·출석 통계·영상) 우선순위 재평가
- 필요할 경우 네이티브 앱 또는 오프라인 쓰기 검토

**완료 기준:** 다음 개발 항목을 추측이 아닌 실제 사용 데이터와 피드백으로 선정할 수 있음.

## 6. 핵심 테스트 체크리스트

- [ ] 로그인하지 않은 방문자와 회원의 공개/비공개 데이터 접근이 의도대로 구분된다.
- [ ] A 클럽 회원에게 B 클럽의 경기·명단·푸시가 노출되지 않는다.
- [ ] 한 사용자가 둘 이상의 클럽에 속해도 클럽 전환이 정확하다.
- [ ] 관리자/소유자 권한으로만 가능한 기능을 일반 회원이 호출할 수 없다.
- [ ] Android Chrome에서 설치/오프라인 조회/알림이 동작한다.
- [ ] iPhone Safari의 '홈 화면에 추가' 이후 푸시 권한 요청과 수신이 동작한다.
- [ ] 알림 권한 거부, 구독 만료, 기기 변경 시 오류 없이 복구된다.
- [ ] 알림 클릭이 정확한 클럽·경기·공지 화면으로 연결된다.
- [ ] 인터넷 연결 차단 시 오래된 데이터임을 명확히 표시한다.
- [ ] 로그아웃 및 클럽 전환 시 이전 사용자/클럽의 민감 캐시가 노출되지 않는다.
- [ ] 배포/롤백/Service Worker 업데이트 후 구버전 캐시로 오류가 발생하지 않는다.
- [ ] 기존 실시간 중계·대회 관리·통계 화면에 회귀 문제가 없다.

## 7. 우선순위 및 설계 의사결정

| 우선순위 | 항목 | 판단 |
|---|---|---|
| P0 | 모바일 홈, 일반 회원 사용 흐름, 클럽별 권한 | 제품 가치와 안전성의 중심 |
| P0/P1 | 참석 응답 및 운영진 확인 | 실제 클럽 업무에 필요하다면 P0 |
| P1 | PWA 설치 지원 | 작은 변경으로 배포 경험 개선 |
| P1 | 클럽별 Web Push | 핵심 차별 경험; 운영 안정성 요구 |
| P2 | 일정·결과 오프라인 읽기 | 유용하지만 온라인 사용을 우선 |
| P3 | 오프라인 입력·자동 충돌 해결 | 실사용 수요 확인 후 |
| 보류 | 네이티브 앱, 유료 결제, PostgreSQL, WebSocket 전환 | 현 단계 목표 밖 |

## 8. 최종 방향

**FCManager는 이미 멀티테넌트 구조와 배포 체계를 갖춘 서비스다.** 이번 프로젝트는 새로운 SaaS를 만드는 일이 아니라, 기존의 경기·대회 관리 기능 위에 **일반 회원용 모바일 경험, PWA 설치, 클럽별 알림, 제한적 오프라인 조회**를 더하는 작업이다.

개발은 첫 실사용 축구회를 기준으로 단순하게 진행하되, 테넌트 격리·권한·배포 계약은 처음부터 모든 클럽에 동일하게 적용한다. 웹에서 실제로 해결할 수 없는 제약이 나타날 때에만 네이티브 전환을 검토한다.
