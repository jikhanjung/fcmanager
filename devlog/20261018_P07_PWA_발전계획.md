## 0. 결정 요약 (2026-10-18)

| 항목 | 결정 |
|------|------|

## 1. 사용자 경험 목표

1. 회원은 스마트폰에서 1~2번 조작으로 **다음 경기 일정**(그리고 회원 체계 이후 **참석 여부**)을 확인한다.
2. 운영진은 일정·변경 사항을 입력하고 **해당 클럽 구독자/회원에게 알림**을 보낼 수 있다.
3. 홈 화면에 추가하면 앱처럼 실행된다(Android/iPhone). 설치는 **선택 사항**.
4. 연결이 불안정해도 최근 받아둔 일정·결과 등 **읽기 전용 정보**는 보인다(오래된 데이터임을 표시).
5. 기존 경기·대회·팀·선수·실시간 중계·운영 기능을 훼손하지 않는다.
6. 첫 클럽(fcsky)에서 실사용 검증하되, 모든 구조는 여러 클럽에 동일하게 적용한다.

## 3. 제품 방향 — 운영진 도구에서 회원 앱으로

강점(경기·대회 관리, 기록, 중계)은 유지하고, 신규 투자는 **일반 회원이 매주 반복하는 흐름**에 둔다.

**모바일 홈(클럽) 구성 후보**
- 다음 경기 카드: 날짜·시간·장소·상대 (+ 집합 시간 필드 신설 시)
- 참석 응답·현황 (회원 체계 이후)
- 최근 공지(고정 공지 우선), 최근 경기 결과 → 상세
- 클럽 이름·엠블럼 반영, 소속 클럽이 여럿이면 클럽 전환

**주간 흐름 (최종 형태)**
1. 운영진이 경기를 등록한다.
2. 운영진이 "알림 보내기"로 클럽 구독자/회원에게 푸시한다(권한 허용 기기만).
3. 회원이 알림을 누르면 해당 클럽의 경기 상세/참석 화면이 열린다.
4. 회원이 참석 여부를 응답한다 → 운영진이 현황을 보고 미응답자에게 재알림.
5. 경기 후 기존 결과·이벤트·통계 기능을 그대로 쓴다.

## 4. 회원 체계 (일반 설계)

> 이 절은 **방향과 선택지**만 정한다. 인증 방식·공개 범위 등 세부 결정은 착수 시점에
> 첫 클럽의 운영 관행을 보고 확정한다(§8 미결정 사항).

### 4.1 역할 모델

`ClubMembership.Role` 에 **`MEMBER`(회원)** 를 추가해 3단 계층으로 둔다.

| 역할 | 할 수 있는 일 |
|------|---------------|
| OWNER (소유자) | STAFF 권한 전부 + 클럽 멤버십(운영진·회원) 구성 관리 (`club_owner_required`, 기존) |
| STAFF (운영진) | 데이터 입력(경기·명단·공지·중계), 회원 초대·승인, 알림 발송, 참석 현황 열람 |
| MEMBER (회원) | 공개 정보 열람 + 본인 참석 응답 + 본인 알림 설정 + (공개 범위 결정 시) 회원 전용 정보 열람 |
| 비로그인 방문자 | 공개 정보 열람 + 클럽 단위 푸시 구독(§5.3) |

- 사용자는 클럽마다 역할이 다르다(A 클럽 STAFF, B 클럽 MEMBER) — 기존 `unique_together(user, club)` 유지.
- 역할 승급/강등은 OWNER 만. **마지막 OWNER 보호** 규칙은 그대로.
- 기본값: 현재 `default=STAFF` → MEMBER 도입 시 **새 멤버십 기본값은 MEMBER** 로 바꾸는 것을 검토
  (기존 행은 데이터 마이그레이션 없이 그대로 STAFF/OWNER).

### 4.2 권한 판정 정비 (MEMBER 추가의 선행 조건)

- ⚠️ `is_club_staff()` 는 지금 `ClubMembership.objects.filter(user, club).exists()` — 역할을 보지 않는다.
  MEMBER 를 추가하는 **같은 변경 안에서** `role__in=(OWNER, STAFF)` 로 좁히고, 회귀 테스트를 먼저 쓴다
  ("MEMBER 는 `@club_staff_required` 뷰에서 403").
- 새 판정 `is_club_member(user, club)` (= 어떤 역할이든 멤버십 존재) 와 데코레이터 `club_member_required` 신설.
- 템플릿의 조건부 관리 링크·컨텍스트 프로세서가 staff 판정을 어떻게 쓰는지 전수 점검.
- 원칙: 권한은 **서버에서** 판정한다. 버튼 숨김은 UX 일 뿐 보안 경계가 아니다.

### 4.3 계정 획득 · 온보딩

지금은 계정을 admin 에서만 만든다. 회원 규모(수십 명)·연령대(50대 아마추어)를 고려하면 **가입 마찰**이
가장 큰 변수다. 후보:

| 방식 | 장점 | 단점 |
|------|------|------|
| A. 운영진이 계정 생성 후 전달 | 구현 최소, 통제 쉬움 | 운영진 부담, 비밀번호 전달 문제 |
| B. **클럽 초대 링크/QR → 회원 가입 → 운영진 승인** | 셀프 서비스, 클럽 귀속이 자연스러움 | 가입 폼·승인 화면 필요, 아이디/비번 부담은 남음 |
| C. 회원별 개인 링크(토큰, 매직 링크) | 아이디/비번 없이 1탭 진입 | 링크 유출 = 계정 유출, 재발급·폐기 관리 필요 |
| D. 소셜 로그인(카카오 등) | 익숙함, 비번 없음 | 외부 의존·앱 등록, 범위 확대 |

- 기본 방향: **B 를 골격**으로 두고, 마찰이 크면 C 를 보조 수단으로 검토. D 는 이 단계 비범위.
- 초대 토큰은 클럽 FK·만료·사용 횟수 제한·폐기 가능하게. 초대로 들어온 사람은 **승인 전 MEMBER 권한 없음**.
- 가입 정보는 최소화(이름·아이디·비밀번호). 연락처·이메일은 필요가 확인될 때만 수집.
- 비밀번호 분실 처리: 이메일 미수집이면 **운영진 재설정** 경로(OWNER/STAFF 화면)로.

### 4.4 계정 ↔ 선수 연결

- 회원(계정)과 선수(`Player`)는 별개 개념으로 유지한다 — 선수 기록은 계정 없이도 존재하고(과거 선수·상대 경기),
  계정은 선수가 아닌 회원(매니저·코치·후원회원)도 가질 수 있다.
- 연결은 **클럽 단위**: `ClubMembership.player`(nullable FK, 같은 클럽의 Player 로 제한) 가 1순위 후보.
  `Player` 는 이미 클럽 스코프라 한 사람이 여러 클럽에 있으면 클럽별 Player 가 따로 있다 — 멤버십에 다는 쪽이 맞는다.
- 연결 주체: 운영진이 지정(기본) 또는 회원이 요청 → 운영진 승인. 한 Player 에 두 계정 연결 금지.
- 연결 결과 활용: "내 팀(TeamMembership 기준) 다음 경기", 참석 대상자 산정, 선수 상세에서 본인 표시.

### 4.5 생애주기

| 이벤트 | 처리 |
|--------|------|
| 가입/초대 수락 | 승인 대기 → STAFF 승인 시 MEMBER |
| 탈퇴/제명 | 멤버십 삭제. **선수 기록·과거 참석 기록은 보존**(Player 는 soft delete 관례), 해당 클럽 푸시 구독 해지 |
| 계정 삭제 | 전 클럽 멤버십 삭제, 사용자 연결 구독 삭제 |
| 클럽 전환 | 세션은 공유(단일 오리진). 화면은 항상 현재 슬러그(`request.club`) 기준으로만 조회 |

### 4.6 공개 범위

- 현재는 거의 전부 공개. 회원 체계가 생기면 **"회원 전용" 정보를 둘지**를 결정해야 한다
  (예: 참석 현황, 회원 연락처, 내부 공지). 기본값은 **현행 공개 유지 + 참석 현황만 회원 전용**.
- 회원 전용 정보가 생기면 오프라인 캐시 규칙(§5.4)과 백업 반출 위생에 영향 — 같이 갱신.

### 4.7 관리 화면 · admin

- 운영진 웹(`/manage/`)에: 회원 목록·승인 대기·초대 링크 발급/폐기·선수 연결·역할 변경(OWNER).
- admin 에도 등록(검색·필터·autocomplete) — 프로젝트 관례(백업/보조 경로).

### 4.8 테스트 (회원 체계)

- MEMBER 가 staff/owner 전용 뷰 전부에서 403 (URL 목록 기반 일괄 테스트).
- A 클럽 MEMBER 가 B 클럽 회원 전용 정보·참석 현황에 접근 불가.
- 초대 토큰 만료·폐기·타 클럽 토큰 재사용 차단.
- 마지막 OWNER 보호 회귀.

## 5. 기술 변경

### 5.1 PWA 설치

- **경로**: `TenantMiddleware.PLATFORM_SEGMENTS` 에 `sw.js` 추가하고, 루트 `/sw.js` 를 **뷰로 서빙**
  (WhiteNoise 해시 파일명·`/static/` scope 제약 회피, `Cache-Control: no-cache`). scope 는 `/` 하나.
  슬러그에는 `.` 이 들어갈 수 없어 충돌은 없지만, 미들웨어 통과 처리는 필요.
- **manifest 는 클럽별**: `/<slug>/manifest.webmanifest` — 테넌트 라우팅 덕에 비용이 작다.
  `name`=클럽명, `start_url`·`scope`=`/<slug>/`, `display: standalone`. 아이콘 192/512 는 클럽 로고를
  Pillow 로 리사이즈(로고 없으면 플랫폼 기본 아이콘). 플랫폼 루트용 기본 manifest 도 하나.
- `<link rel="manifest">`·`theme-color`·`apple-touch-icon` 을 `base.html` 에 (현재 클럽 기준).
- 설치 실측: Android Chrome, iPhone Safari "홈 화면에 추가".

### 5.2 모바일 UX

- 일반 회원용 클럽 홈(§3) — 기존 페이지 연결 유지, 운영진 화면과 분리.
- 터치 영역·탐색 동선 점검, 네트워크 오류·빈 데이터·권한 부족 상태 표시.
- 기존 부채 "행 클릭 스크립트 템플릿마다 중복 → base.html 공통 JS" 를 이 작업에서 같이 정리할 여지.

### 5.3 Web Push

**구독 단위 — 두 층**
1. **클럽 단위(익명)**: 로그인 없이 "이 클럽 알림 받기" → 구독을 `club` 에만 묶는다. 회원 체계 없이 가능.
2. **회원 단위**: 로그인 사용자의 구독에 `user` 를 추가로 묶음 → 참석 재알림 등 개인 대상 발송.

모델 후보 `PushSubscription(club, user=null, endpoint unique, p256dh, auth, created_at, last_success_at, failed_count)`.

**발송**
- 저장 시 자동 발송 **안 함** — 일정 일괄 입력(devlog 093 `.md` 입력)·오타 수정마다 알림이 쏟아진다.
  공지·경기 화면에 운영진의 **"회원에게 알림 보내기"** 액션(미리보기·대상 수 표시).
- 요청 안에서 동기 발송 **안 함** — sync 워커 3개라 수십 건 발송이 워커를 묶는다.
  **`PushOutbox` 테이블에 적재 → cron(분 단위) 관리 명령이 발송**. 중복 억제·발송 로그·재시도가 같은 곳에서 해결.
- 410/404 응답 구독은 삭제, 반복 실패는 비활성. 알림 클릭 → 해당 클럽 경기/공지 URL.
- 초기 이벤트: 새 경기 일정 / 일정·장소 변경·연기·취소 / 공지 / (회원 체계 이후) 참석 미응답 재알림.

**키·반출 위생 (이 프로젝트 고유 위험)**
- ⚠️ **테스트 target(m710q :8005)은 운영 DB 스냅샷을 매일 받는다.** 같은 VAPID 키면 테스트 서버가
  **실회원에게 푸시를 보낼 수 있다**. → **target 별 VAPID 키 분리**(구독은 생성 시 공개키에 묶이므로
  다른 키로는 푸시 서비스가 거부) + 테스트 target 에서 발송 cron 비활성.
- 구독 테이블을 0.6.25 반출 위생(`django_session` 제거)과 같은 선상에서 검토 — hourly 스냅샷에서
  제거하거나 비우는 것이 유력(복원 시 구독은 재구독으로 회복 가능).
- VAPID 개인키는 `.env` → m710q·**NAS(0777)** 로 백업된다. NAS 권한 미해결 항목의 무게가 커진다 — 착수 전 정리.
- 배포 계약: 새 env 키는 `DEPLOY.md` 릴리스 델타 노트에, 발송 cron 은 운영 호스트 설정으로 기록.

**클라이언트**
- 권한 요청은 사용자의 명시적 조작 이후에만. SW 에서 `push`/`notificationclick` 처리.
- iPhone 은 iOS 16.4+ **홈 화면 추가된 웹앱에서만** 푸시 — 일반 Safari 탭과 구분해 안내.
- 푸시를 유일한 공지 수단으로 가정하지 않는다(공지 페이지·카톡 병행 전제).

### 5.4 오프라인 읽기

- SW 는 **비로그인·공개 GET 응답만** 캐시. `Vary: Cookie` 가 붙거나 로그인 사용자 응답·관리 화면·
  `live.json`(중계)은 캐시하지 않는다. 현 사이트는 거의 전부 공개라 이 규칙으로 충분하다.
- 앱 셸(CSS/JS/아이콘)은 Cache Storage, 일정·최근 결과는 network-first + 캐시 폴백.
  IndexedDB 는 구조화 데이터가 필요해질 때만.
- "오프라인 — 마지막 동기화 HH:MM" 배너. 로그인·푸시 구독·중계·관리 작업은 온라인 필요 명시.
- 로그아웃 응답에 `Clear-Site-Data: "cache"` — 회원 전용 정보(§4.6)가 생겨도 잔존 방지.
- 이미지·영상은 캐시 제외 또는 상한. 브라우저(특히 iOS)가 저장소를 비울 수 있음 — 영구 원본 아님.
- 오프라인 **입력**(참석 응답 대기열 등)은 실수요 확인 후 별건.

### 5.5 배포 · 관측

- 배포 계약(preflight → build → deploy → smoke → rollback) 유지. SW 버전 = `config/version.py` 연동,
  새 버전 감지 시 "새로고침" 안내 → 구버전 캐시 충돌 방지. 롤백 시에도 SW 가 구버전을 고정시키지 않게.
- 기초 지표: 구독 수, 발송 성공/실패, 알림 클릭, (이후) 참석 응답률. 우선 admin/운영진 화면 집계로.
- 테넌트 격리·발송 범위는 테스트용 별도 클럽으로 확인.

## 6. 단계별 실행 계획 (재배열)

> 초안은 참석(회원 체계 필요)을 Phase 1 에 두었다. 실사 결과 회원 체계가 가장 큰 선행 작업이고,
> 푸시·설치는 그것 없이 가능하므로 **가치가 빨리 나오는 쪽부터** 순서를 바꾼다.

| Phase | 내용 | 회원 체계 필요 | 완료 기준 |
|-------|------|:-:|-----------|
| 0 | 코드 실사 | — | **완료**(§2, 2026-10-18). 착수 시 재확인 |
| 1 | 모바일 클럽 홈 + PWA 설치(§5.1·5.2) | ✗ | Android/iPhone 홈 화면 추가·실행·업데이트 정상, 기존 동선 유지 |
| 2 | 클럽 단위 푸시(§5.3 층 1) + 키 분리·반출 위생 | ✗ | 앱이 닫혀 있어도 구독 기기가 해당 클럽 알림만 수신, 테스트 target 은 발송 불가 |
| 3 | 회원 체계(§4) — 권한 정비 → MEMBER → 초대·승인 → 선수 연결 | — | MEMBER 권한 경계 테스트 통과, 첫 클럽 회원 온보딩 가능 |
| 4 | 참석 응답 + 회원 단위 푸시(재알림) | ✓ | 회원이 1~2탭으로 응답, 운영진이 현황·미응답자 확인/재알림 |
| 5 | 오프라인 읽기(§5.4) | ✗ | 비행기 모드에서 동기화된 일정·결과 표시 + 오래된 데이터 안내 |
| 6 | 첫 클럽 실사용(경기 2~4회) → 다음 범위 결정 | — | 설치율·알림 허용률·응답률·마찰 기록으로 후속 항목 선정 |

- Phase 5 는 Phase 1 이후 어느 시점이든 독립 진행 가능.
- 각 Phase 는 별도 작업 devlog + 릴리스. 마이그레이션 있는 릴리스는 `DEPLOY.md` 델타 노트 필수.

### 참석 응답 (Phase 4) 개요

- `MatchAttendance(club, match, membership, status=참석/불참/미정, updated_at)` — `unique(match, membership)`.
- 대상자 = 경기 참가팀의 TeamMembership ↔ 연결된 회원 (§4.4). 미연결 회원도 응답 허용 여부는 결정 사항.
- 응답 마감(킥오프 N시간 전), 게스트(용병) 표기, 출석 집계 — 첫 클럽 운영 규칙 확인 후 확정.
- 클럽 스코핑·권한은 서버 검사. 운영진은 현황 열람 + 대리 응답.

## 7. 테스트 체크리스트

- [ ] 비로그인 방문자 / MEMBER / STAFF / OWNER 의 접근이 의도대로 구분된다.
- [ ] MEMBER 가 운영진·소유자 전용 뷰를 호출할 수 없다(403).
- [ ] A 클럽 회원·구독자에게 B 클럽의 회원 전용 정보·푸시가 노출되지 않는다.
- [ ] 한 사용자가 둘 이상 클럽에 속해도 역할·데이터가 섞이지 않는다.
- [ ] `/sw.js`·`/<slug>/manifest.webmanifest` 가 정상 응답하고 기존 슬러그 라우팅에 회귀가 없다.
- [ ] Android Chrome 설치·오프라인 조회·알림 동작.
- [ ] iPhone 홈 화면 추가 후 푸시 권한 요청·수신 동작.
- [ ] 권한 거부·구독 만료(410)·기기 변경 시 오류 없이 복구.
- [ ] 알림 클릭이 정확한 클럽·경기·공지로 연결.
- [ ] **테스트 target 에서 운영 구독자에게 발송되지 않는다.**
- [ ] 오프라인 시 오래된 데이터임을 표시, 로그인 응답은 캐시되지 않는다.
- [ ] 배포·롤백·SW 업데이트 후 구버전 캐시로 오류가 나지 않는다.
- [ ] 실시간 중계·대회 관리·통계 화면 회귀 없음.

## 8. 미결정 사항 (착수 시 결정)

1. 회원 인증 방식 — 초대+가입+승인(B) 골격에 매직 링크(C) 보조를 붙일지 (§4.3)
2. 회원 전용 정보의 범위 — 참석 현황 외에 무엇을 닫을지 (§4.6)
3. 계정↔선수 연결 주체 — 운영진 지정 vs 회원 요청+승인 (§4.4)
4. 경기 집합 시간 필드 추가 여부
5. 참석 규칙 — 마감 시점, 게스트 처리, 미연결 회원 응답 허용 여부
6. 푸시 구독 테이블의 백업 반출 처리 — hourly 에서 제거 vs 보존 (§5.3)
7. NAS 0777 정리 시점 — VAPID 키 도입 전에 끝낼지

## 9. 우선순위

| 우선순위 | 항목 | 판단 |
|----------|------|------|
| P1 | 모바일 클럽 홈 + PWA 설치 | 작은 변경, 설치 경험 개선, 선행 조건 없음 |
| P1 | 클럽 단위 푸시 | 핵심 차별 경험, 회원 체계 없이 가능. 키 분리·반출 위생이 전제 |
| P1 | 회원 체계 | 참석의 전제. 권한 경계 변경이라 신중하게 |
| P1→P0 | 참석 응답 | 첫 클럽이 실제로 참석 조사를 앱에서 하길 원하면 P0 |
| P2 | 오프라인 읽기 | 유용하지만 온라인 우선 |
| P3 | 오프라인 입력·충돌 해결 | 실수요 확인 후 |
| 보류 | 네이티브 앱, 결제, PostgreSQL, WebSocket 전환 | 현 단계 목표 밖 |

## 10. 최종 방향

FCManager 는 이미 멀티테넌트 구조와 배포 계약을 갖춘 서비스다. 이 계획은 새 SaaS 를 만드는 일이 아니라,
기존 경기·대회 관리 위에 **설치·알림·오프라인 조회**를 먼저 얹고, 그다음 **회원 체계와 참석 응답**으로
일반 회원의 주간 흐름을 완성하는 작업이다. 테넌트 격리·권한·배포 계약·백업 반출 위생은 처음부터 모든
클럽에 동일하게 적용하고, 웹으로 해결할 수 없는 제약이 실제로 나타날 때만 네이티브를 검토한다.
